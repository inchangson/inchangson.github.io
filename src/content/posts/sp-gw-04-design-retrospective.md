Service Delivery Gateway는 기존 클라이언트의 요청 형식을 뒤쪽 서비스의 계약에 맞게 바꾸고, 라우팅 설정을 애플리케이션 밖에서 관리하기 위해 시작했다. 내가 구현한 범위는 특정 라우트의 query parameter를 JSON body로 바꾸는 WebFlux 필터와 Config Server의 파일 기반 설정 조회 및 메모리 캐시, Gateway의 설정 갱신 경로였다.

당시 팀 개발 리드가 요청한 것은 일부 요청에만 별도 파이프라인을 적용하는 것이었다. 요청 형식을 바꾸는 단계뿐 아니라 고객 조회와 동의 확인 같은 인증 절차를 순서대로 수행하고, 각 단계의 결과에 맞는 응답을 반환하는 구상이었다. 제공된 소스에서는 이 파이프라인의 구현 완료를 확인하지 못했다. 이 글에서는 확인된 구현과 당시 요구사항을 먼저 나눈 뒤, 별도 Pod로 운영할 이유와 DB를 사용하는 인증 책임의 위치를 현재 시점에서 다시 검토한다.

## 내가 맡은 범위와 확인된 결과

요청 변환은 모든 트래픽에 적용하지 않고 라우트 설정으로 선택한 요청에만 적용했다. 필터는 제외할 query 이름을 받고, 단일 값은 문자열로, 복수 값은 배열로 보존해 JSON body를 만든다. 자세한 입력 계약과 기존 body 처리 방식은 [1편](/blog/sp-gw-01-request-contract)에 정리했다.

설정 관리에서는 Spring Cloud Config의 native repository를 새로 구현하지 않았다. 프레임워크가 생성한 첫 번째 native repository를 wrapper로 감싸고, YAML 해석과 profile 병합은 delegate에 맡겼다. wrapper는 파일 수정 시각으로 state를 만들고 `application:profile:state` 키로 완성된 `Environment`를 프로세스 메모리에 저장한다. 캐시 hit에서도 파일 metadata는 확인하며, 대상 파일을 찾지 못하거나 cache miss가 나면 delegate를 호출한다.

이 선택의 의미는 파일시스템 설정과 메모리 설정을 같은 것으로 취급하지 않는 데 있다. 파일은 변경 여부를 판단하는 원본이고, 메모리에는 이미 해석된 응답 객체가 있다. 파일 수정 시각이 달라지면 새 키로 다시 구성하고 이전 키를 정리한다. 프레임워크의 설정 해석을 유지하면서 state와 재사용 정책만 덧붙인 composition이 이 프로젝트에서 가장 의미 있는 설계 성과였다. 구성 방식과 캐시의 정확성 조건은 [Config Server 설계 시리즈 1편](/blog/gateway-config-01-composition-boundary)과 [2편](/blog/gateway-config-02-filesystem-memory-cache)에서 더 자세히 다뤘다.

Gateway 쪽에서는 라우트 정의를 외부 설정으로 옮기고 Config Client, RabbitMQ 기반 Cloud Bus, 주기적인 자기 refresh 호출을 연결했다. 기준 코드의 self-refresh 주기는 1시간이다. 이 구성은 코드 배포와 이미 존재하는 필터의 라우트 설정 변경을 분리하지만, 모든 인스턴스가 같은 순간에 같은 설정을 적용한다는 보장은 아니다. 갱신과 전파의 범위는 [2편](/blog/sp-gw-02-config-refresh), 배포 구성의 범위는 [3편](/blog/sp-gw-03-delivery-boundary), Bus 연결은 [Config Server 설계 시리즈 3편](/blog/gateway-config-03-bus-rabbitmq)에서 확인할 수 있다.

## 당시 요구사항이 넓힌 문제의 성격

확인된 구현과 당시 요구사항은 모두 Gateway 필터 체인으로 표현할 수 있지만 책임의 종류는 다르다.

| 구분 | 확인된 구현 | 당시 요구사항 |
|---|---|---|
| 적용 범위 | 설정으로 선택한 라우트 | 일부 요청에만 별도 파이프라인 적용 |
| 처리 내용 | query를 JSON body로 변환 | 요청 변환, 고객 조회, 동의 확인을 단계별 수행 |
| 필요한 상태 | 요청과 라우트 설정 | 고객 및 동의 업무 데이터 |
| 실패 응답 | 변환 또는 하위 서비스 응답 | 단계별 판정에 맞는 응답 |
| 근거 수준 | 소스와 이력에서 확인 | 팀에서 전달받은 요구사항이며 제공된 소스에서 구현 완료를 확인하지 못함 |

형식 변환은 경계에서 두 HTTP 계약을 맞추는 기술 책임이다. 토큰 서명과 만료, API key 형식처럼 요청 자격 정보를 검증하는 일도 여러 서비스에 공통인 진입 정책으로 둘 수 있다. 반면 고객이 누구인지 조회하고 동의 상태가 유효한지 판단하는 일은 업무 데이터와 정책의 의미를 알아야 한다. 전자는 자격 정보의 유효성을 확인하는 인증에 가깝고, 후자는 고객 상태를 근거로 요청 허용 여부를 정하는 업무 권한 판단에 가깝다. 처리 단계를 하나의 체인으로 연결할 수 있다는 사실만으로 같은 애플리케이션이 그 책임을 소유해야 하는 것은 아니다.

현재 소스에는 API key와 JWT를 다루는 공동 구현이 있지만, 이것만으로 내가 모든 인증 코드를 구현했다고 말할 수 없다. 고객 조회와 동의 확인 파이프라인의 Java 구현 근거도 확인되지 않는다. 또한 이력에는 R2DBC 기반 기능을 제거하고 별도 모듈에서 처리할 예정이라고 기록한 변경이 있다. 이 기록은 Gateway의 DB 접근을 일반적으로 금지한다는 원칙이 아니라, 당시 코드에서도 데이터 의존 기능을 분리하는 방향이 나타났다는 근거로만 사용한다.

## 별도 Pod는 변환 기능만으로 충분한가

별도 Gateway를 배포하면 독립적으로 확장하고 장애와 배포 주기를 분리할 수 있다. 그 대신 네트워크 구간, 관측 대상, 인증서와 설정, 배포 파이프라인, 장애 지점도 하나씩 늘어난다. 요청 변환 규칙 하나만 있고 기존 Gateway에 같은 라우트 필터를 안전하게 붙일 수 있다면, 별도 Pod의 운영 비용이 얻는 이점보다 클 수 있다.

반대로 여러 기존 클라이언트의 계약 차이를 한곳에서 흡수하고, 라우트별 적용 정책과 설정 갱신을 독립적으로 운영해야 한다면 별도 배포 단위가 의미를 갖는다. 판단 기준은 “Gateway 기술을 사용했는가”가 아니라 다음 질문이어야 한다.

- 변환 규칙의 변경 주기와 배포 주기가 기존 진입점과 실제로 다른가
- 별도 확장이나 장애 격리가 필요한 트래픽 특성이 있는가
- 이 컴포넌트가 여러 서비스가 공유하는 경계 정책을 일관되게 적용하는가
- 추가 네트워크 hop과 운영 요소를 감수할 만큼 독립 운영의 이점이 있는가

지금 돌아보면 query-to-JSON 변환 자체는 별도 Pod의 충분조건이 아니다. 이 구현의 더 큰 가치는 라우트별 계약 변환, 외부 설정, 갱신 경로를 한 경계에서 관리할 수 있게 만든 데 있다. 별도 배포를 유지하려면 그 경계가 실제로 여러 서비스에서 공유되고 독립 운영이 필요하다는 근거를 함께 제시해야 한다.

## DB가 필요한 인증 절차는 어디에 둘 것인가

Gateway가 DB에 접근하면 안 된다는 절대 규칙은 없다. 다만 고객 테이블과 동의 상태를 직접 조회하는 순간 Gateway는 저장 구조, 업무 상태, 데이터 장애에 결합된다. DB 응답이 느리면 해당 조회를 수행하는 라우트의 지연이 늘고, connection pool 같은 공유 자원이 고갈되면 영향이 다른 요청으로 번질 수도 있다. 재시도와 timeout, 데이터 변경 시점도 Gateway의 운영 문제에 들어온다. 인증 판단에 여러 테이블과 변경 트랜잭션이 필요해질수록 결합은 더 커진다.

현재 시점에서 선호하는 경계는 인증 서비스가 고객 조회와 동의 정책을 소유하고, Gateway는 요청에서 자격 정보를 추출한 뒤 인증 서비스의 판정 결과를 라우팅에 사용하는 방식이다. 인증 서비스는 단계별 내부 처리 결과를 외부에 그대로 노출하기보다 허용, 인증 필요, 동의 필요처럼 안정된 판정 계약으로 반환할 수 있다. Gateway는 그 계약을 HTTP 상태와 응답 형식으로 매핑하고, 허용된 요청에 필요한 식별 문맥을 전달한다.

이 구조에서도 요청마다 동기 호출하면 인증 서비스가 진입 경로의 의존성이 된다. 따라서 판정 API 계약에 timeout, 재시도 가능 여부, 고객 없음, 동의 필요, 내부 오류에 대응하는 결과를 명시하고 Gateway의 HTTP 응답 매핑을 함께 정해야 한다. 상관관계 ID와 단계별 지표도 필요하다. 이 선택은 DB 결합을 없애기보다 업무 데이터의 소유권과 실패 처리를 인증 서비스 쪽에 모은다.

고객 조회가 단순하고 데이터가 Gateway 전용이며 독립된 저장 모델을 갖는다면 Gateway 내부 조회도 선택지가 될 수 있다. 하지만 공유 고객 DB의 스키마를 직접 읽고 동의의 업무 의미까지 해석해야 한다면 인증 서비스로 분리하는 편이 변경 영향과 책임을 설명하기 쉽다.

## 지금 비교하는 대안과 trade-off

아래 대안은 당시 모두 검토했다는 기록이 아니라, 구현과 당시 요구사항을 바탕으로 현재 시점에서 비교한 결과다.

| 대안 | 잘 맞는 조건 | 주요 비용과 위험 |
|---|---|---|
| 기존 Gateway의 라우트 필터 | 변환 규칙이 작고 기존 진입점과 배포 주기가 같음 | 기존 Gateway의 회귀 범위가 넓어질 수 있음 |
| 별도 Service Delivery Gateway | 여러 서비스가 같은 경계 정책을 공유하고 독립 배포와 확장이 필요함 | hop과 운영 요소, 장애 지점 증가 |
| 변환 전용 adapter 서비스 | 특정 하위 서비스의 계약 차이가 크고 그 서비스와 함께 변경됨 | 공통 정책이 여러 adapter로 흩어질 수 있음 |
| Gateway가 고객 DB 직접 조회 | 데이터가 단순하고 Gateway가 저장 모델을 명확히 소유함 | 스키마와 업무 정책, DB 장애가 진입 경로에 결합 |
| 인증 서비스에 판정 위임 | 고객과 동의 정책을 한 서비스가 소유하고 여러 진입점이 재사용함 | 동기 호출의 지연과 가용성, 판정 API의 버전 관리 필요 |

Gateway offloading은 인증이나 프로토콜 변환처럼 여러 서비스의 공통 기능을 진입점으로 옮기는 패턴이다. 동시에 Gateway가 뒤쪽 서비스의 업무 책임까지 계속 흡수하면 변경과 장애의 집중점이 될 수 있다. [Microsoft의 Gateway Offloading 패턴 설명](https://learn.microsoft.com/en-us/azure/architecture/patterns/gateway-offloading/)도 공통 기능을 Gateway로 옮길 때 결합, 단일 장애점, 서비스별 요구 차이를 함께 검토하도록 안내한다.

## 구현과 검증을 어떻게 이어갈 것인가

당시 요구한 인증 파이프라인을 실제로 만든다면 먼저 “일부 요청”을 라우트와 predicate로 명시하고, 각 단계의 입력과 출력 계약을 정하겠다. 토큰이나 API key의 기술 검증과 고객 조회 및 동의 판단의 업무 책임도 분리한다. 고객 조회와 동의 판단은 인증 서비스의 API로 두고, Gateway에는 호출 순서와 최종 응답 매핑만 둔다. 단계 이름이나 내부 테이블 상태를 그대로 응답 코드로 만들지 않아야 서비스 내부 변경이 외부 계약을 흔들지 않는다.

검증은 정상 응답만 확인해서는 부족하다. 변환 대상이 아닌 라우트가 영향을 받지 않는지, 고객 없음과 동의 필요를 구분하는지, 인증 서비스 timeout과 오류에서 계약에 정한 응답을 반환하는지, 재시도로 같은 요청을 중복 처리하지 않는지를 확인해야 한다. 두 개 이상의 Gateway 인스턴스에서는 설정 변경 전후의 라우트와 판정 버전도 함께 기록해야 한다.

현재 구현 검증은 소스와 비공개 변경 이력, 기존 Config Server 부하 실험을 근거로 한다. 부하 실험은 파일 기반 설정 응답과 캐시 동작을 확인한 것이며, 고객 조회나 동의 확인 파이프라인의 성능을 검증한 결과가 아니다. 이 구분을 유지해야 설정 관리 성과를 당시 인증 요구의 성과로 확대하지 않게 된다.

## 결과와 회고

이 프로젝트에서 확인할 수 있는 결과는 라우트별 요청 변환을 구현하고, 외부 라우트 설정을 파일과 메모리의 경계를 나눠 제공하며, Config와 Bus를 통해 실행 중인 Gateway의 갱신 경로를 구성했다는 것이다. 특히 native repository를 composition으로 감싼 설계는 프레임워크의 해석 책임을 보존하면서 변경 감지와 캐시 정책을 추가했다.

당시 인증 요구를 함께 놓고 보면 아키텍처 판단 기준도 더 선명해진다. 별도 Gateway는 변환 코드의 양이 아니라 독립 운영해야 할 공통 경계가 있는지로 판단해야 한다. 고객 조회와 동의 확인은 필터 체인으로 구현할 수 있는가보다 누가 업무 데이터와 정책을 소유하는가를 먼저 물어야 한다. 나는 현재라면 Gateway에는 선택적 적용과 안정된 판정 계약의 집행을 두고, RDB에 의존하는 고객 및 동의 판단은 인증 서비스에 두는 방향을 우선 검토하겠다. 실제 데이터 소유권과 가용성 요구가 다르면 그 근거에 따라 다시 결정할 수 있다.
