UUID는 중앙 발급 서버 없이 여러 노드에서 충돌 가능성이 매우 낮은 128비트 식별자를 만들 수 있다. 분산 환경과 외부 공개 ID에 유용하지만, 정수형 자동 증가 키보다 저장 공간과 인덱스 비용이 크다.

## 주요 형태 비교

| 종류 | 생성 기준 | 정렬 특성 | 주의점 |
|---|---|---|---|
| UUID v4 | 난수 | 생성 순서와 무관 | B-tree 인덱스 삽입 위치가 분산됨 |
| UUID v7 | Unix 시간 + 난수 | 대체로 시간순 | 생성 시각이 식별자에 드러남 |
| Auto Increment | DB 순번 | 증가 순서 | 중앙 DB 의존, 개수 추측 가능 |

새 시스템에서 랜덤 UUID의 인덱스 지역성이 문제가 된다면 시간 순서로 정렬 가능한 UUID v7을 검토할 수 있다. 다만 사용 중인 언어, 라이브러리, 데이터베이스의 지원 상태를 먼저 확인해야 한다.

## 데이터베이스 저장

가능하면 문자열 `varchar(36)`보다 데이터베이스의 native UUID 타입 또는 16바이트 이진 타입을 사용한다.

```sql
create table orders (
    id uuid primary key,
    customer_id uuid not null,
    created_at timestamptz not null
);
```

문자열 저장은 읽기에는 편하지만 하이픈과 문자 표현 때문에 더 많은 공간을 사용하고 비교 비용도 늘어난다. 애플리케이션과 DB 드라이버가 UUID 타입을 직접 지원한다면 변환 책임도 줄어든다.

## 내부 키와 외부 키 분리

데이터가 많고 join 성능이 중요하면 내부 PK는 정수형으로 유지하고 외부 노출용 UUID를 별도 unique column으로 둘 수 있다.

```sql
create table orders (
    id bigint generated always as identity primary key,
    public_id uuid not null unique,
    created_at timestamptz not null
);
```

이 방식은 인덱스와 FK 크기를 줄이지만 식별자가 두 개가 되어 매핑과 제약 조건 관리가 늘어난다. 실제 부하와 운영 편의성을 측정한 뒤 선택한다.

## UUID는 권한 검사가 아니다

UUID는 숫자 순번보다 추측하기 어렵지만 비밀값은 아니다. URL, 로그, 브라우저 기록, 분석 도구를 통해 노출될 수 있다.

```text
GET /orders/018f... 
```

서버는 UUID를 안다는 이유만으로 접근을 허용하면 안 된다. 항상 현재 사용자가 해당 주문을 읽거나 수정할 권한이 있는지 확인해야 한다.

## 생성 위치

- 애플리케이션 생성: DB 저장 전부터 식별자가 있어 이벤트와 하위 객체에 사용하기 쉽다.
- 데이터베이스 생성: 생성 규칙을 한곳에 모을 수 있지만 insert 후 값을 받아야 한다.
- 여러 서비스가 생성: 같은 UUID 버전과 표현 형식을 합의해야 한다.

분산 이벤트를 먼저 만들고 나중에 저장하는 구조라면 애플리케이션에서 생성하는 편이 자연스럽다.

## 선택 체크리스트

- 여러 노드가 DB 왕복 없이 ID를 생성해야 하는가?
- 외부에 순차 ID를 노출하지 않아야 하는가?
- 쓰기량과 인덱스 단편화가 문제가 되는가?
- 사용 기술이 native UUID 또는 UUID v7을 지원하는가?
- 생성 시각 노출이 허용되는가?
- 식별자와 별개로 객체 수준 권한 검사를 수행하는가?
