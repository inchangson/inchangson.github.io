이력서에는 결과를 짧게 쓰고, 면접에서는 그 결과를 만든 선택을 설명해야 한다. 이 시리즈는 실제 구현에서 시작해 다른 선택지와 실패 상황까지 질문을 이어 간다. 답변 예시는 암기용 문장보다 내 경험을 확인하는 기준으로 쓴다.

## 경험별로 이어질 질문

| 이력서의 출발점 | 첫 질문 | 이어지는 질문 | 준비 글 |
|---|---|---|---|
| 설정을 메모리에 캐싱 | 어떤 캐시인가? | 다른 서버, 변경 감지, Redis와의 차이, 동시 miss는? | [1편: 캐시와 일관성](/blog/interview-prep-01-cache-consistency) |
| Gateway 요청 변환과 설정 외부화 | 기존 계약을 어떻게 보존했나? | 복수 값, body, 비동기 처리, 갱신 완료, 성능 수치는? | [2편: Gateway와 측정](/blog/interview-prep-02-gateway-performance) |
| 고객 인증과 계정 복구 | 같은 요청이 동시에 오면? | PKCE, 토큰 교체, DB 잠금, OTP, SMS 실패는? | [3편: 인증과 동시성](/blog/interview-prep-03-auth-concurrency) |
| VM별 배포와 외부 API 공통화 | 실패 범위를 어떻게 줄였나? | 관리 ID, 기동 확인, timeout, 연결 풀, 재시도는? | [4편: 배포와 외부 연동](/blog/interview-prep-04-delivery-external-api) |

## 1분 답변은 다섯 문장으로 시작한다

1. **규모와 역할:** 어떤 서비스에서 어느 부분을 맡았는가.
2. **문제:** 기존 방식으로 무엇이 불편하거나 위험했는가.
3. **선택:** 어떤 제약 때문에 이 방식을 택했는가.
4. **검증과 결과:** 무엇을 바꿨고 어떻게 확인했는가.
5. **남은 문제:** 아직 보장하지 못한 조건은 무엇인가.

예를 들어 배포 경험은 이렇게 시작할 수 있다.

> 여러 고객 사이트의 CI/CD를 구축하고 운영 배포를 개선했습니다. 한 번의 실행이 여러 VM을 바꾸는 구조라 변경 범위를 줄일 필요가 있었습니다. 사이트별 설정은 유지하면서 실행 대상을 한 VM으로 제한하고, 원격 스크립트의 실패를 Jenkins에 전달했습니다. 비밀값도 Jenkins가 전달하는 대신 대상 VM이 관리 ID로 조회하게 바꿨습니다. 다만 자동 롤백과 배포 후 기동 확인까지 구현한 것은 아닙니다.

여기서 “한 VM이면 무중단인가요?”라는 질문이 나오면 4편의 트래픽 제외, 기동 확인, 롤백 순서로 이어 간다. 답변에 기술명을 많이 넣기보다 실제로 바꾼 범위를 분명히 말하는 편이 낫다.

## 수치에는 측정 조건을 붙인다

| 준비된 근거 | 말할 수 있는 것 | 그 수치로 알 수 없는 것 |
|---|---|---|
| 플랫폼 20개 서비스, 38 Pod 구성 | Config 조회 부하를 모사할 때 사용한 규모 | 실제 38 Pod를 띄운 E2E 결과 |
| 로컬 Config 반복 조회 1,900건, p95 11.223ms | 한 프로세스의 짧은 반복 조회 실험 결과 | 운영 최대 RPS, Redis 대비 성능, 캐시 도입 전후 개선 배수 |
| 여러 고객 사이트, 실행 대상 VM 1대 | 배포 한 번의 변경 범위 | 장애율이나 배포 시간 감소율 |
| 계정 복구의 개발계 테스트 | 구현한 실패 처리와 검증 조건 | 운영 이용자 수, 운영 장애 감소율 |

쿠폰 인덱스 개선은 보조 경험으로 짧게 준비한다. 전체 수 집계를 기존 묶음 수량으로 대체했고 사용 수 집계에 복합 인덱스를 추가했다. 단일 실행 계획에서 34.802ms가 14.510ms로 바뀌었지만, 운영 API 전체가 같은 비율로 빨라졌다는 뜻은 아니다. 이어질 질문은 인덱스 컬럼 순서, `COUNT(DISTINCT)`의 의미, Index Only Scan의 힙 접근 조건이다. 자세한 측정 기록은 저장소의 `src/content/posts/coupon-statistics-query-optimization.md`에 있다.

## 질문을 받았을 때 근거를 찾는 순서

각 편은 구현 파일과 심볼, 필요하면 기준 커밋을 적는다. 원본이 비공개인 경우 존재하지 않는 공개 링크를 만들지 않고 경로로 남긴다. 실행 가능한 학습 모델은 원본 서비스의 통합 테스트와 구분한다.

- **내가 구현한 동작:** 코드와 변경 이력으로 답한다.
- **라이브러리가 보장하는 동작:** 해당 버전의 공식 문서와 소스로 답한다.
- **얼마나 좋아졌는가:** 실험 조건과 원시 결과로 답한다.
- **다시 설계한다면:** 제안이라고 밝히고, 필요한 검증을 설명한다.

문서를 읽었다고 당시 그 대안을 검토한 것은 아니다. Redis 비교 수치가 없다면 없다고 말하고, 어떤 조건을 맞춰 비교할지 설명한다. 이 구분을 지키면서 각 편의 첫 답변을 1분 안에 말하고 꼬리 질문 두세 개를 이어서 연습한다.
