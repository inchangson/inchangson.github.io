PostgreSQL 메모리 알람 시간대의 로그와 APM을 대조하다 쿠폰 통계 조회를 느린 쿼리 후보로 찾았다. 이후 전체 수 집계를 저장된 수량 조회로 바꾸고, 사용 수 집계에 복합 인덱스를 운영 반영했다.

## 전체 수는 저장된 값을 읽도록 변경

기존 API는 쿠폰 묶음의 전체 발급 수를 원장 `COUNT`로 구했다. 묶음에 이미 수량이 저장돼 있어 해당 값을 읽도록 바꿨다. 사용 수와 미할당 수는 의미가 다른 집계이므로 이 변경을 그대로 적용하지 않았다.

전제는 **묶음 수량과 실제 생성된 쿠폰 수가 일치한다**는 것이다. 코드에는 업로드 파일의 행 수와 묶음 수량을 대조하는 방어 로직이 있지만, 모든 생성 및 수정 경로의 정합성을 증명하지는 못한다. 재발급, 취소, 무효화가 전체 수에 미치는 영향도 확인해야 한다.

## 사용 수에는 복합 인덱스 적용

사용 수는 발급 이력에서 묶음별 `COUNT(DISTINCT coupon_id)`로 구한다. 한 쿠폰에 여러 이력이 생길 수 있어 `DISTINCT`는 유지했다.

기존 계획은 대상 이력 약 10만 건을 얻기 위해 테이블 전체를 순차 스캔한 뒤 정렬했다. `(묶음 식별자, 쿠폰 식별자)` 인덱스를 추가해 묶음으로 범위를 좁히고, 그 안에서 쿠폰 식별자를 읽도록 했다. 사내 스키마와 컬럼 이름은 일반화했다.

한 번의 `EXPLAIN (ANALYZE, BUFFERS)` 비교 결과다.

| 항목 | 적용 전 | 적용 후 |
|---|---:|---:|
| 주요 접근 경로 | Sequential Scan + Sort + Aggregate | Index Only Scan + Aggregate |
| 실행 시간 | 34.802ms | 14.510ms |
| 실행 단계 공유 버퍼 블록 | hit 4,227 | hit 1 + read 386, 합계 387 |
| Heap Fetches | 해당 없음 | 0 |

필요한 컬럼이 인덱스에 있고 해당 힙 페이지가 all-visible 상태여서 `Heap Fetches: 0`이 가능했다. 쓰기로 Visibility Map 상태가 바뀌면 같은 쿼리도 힙을 방문할 수 있다. 인덱스의 쓰기 비용과 autovacuum 상태를 함께 봐야 한다.

물리화 뷰와 요약 테이블도 검토했지만 적용하지 않았다. 최신성 지연이나 집계 갱신의 정합성을 추가로 관리하기보다 기존 조회 의미를 유지하는 변경을 택했다. 미할당 수 집계는 후보 인덱스 자료만 있어 최종 적용 범위에서 제외했다.

## 확인한 결과와 남은 검증

확인한 결과는 원장 집계 제거와 사용 수 집계의 실행 계획 변화다. 전후 캐시 상태가 달랐고 단일 측정이므로, 위 시간을 운영 응답시간 개선률로 쓰지는 않는다. 메모리 알람의 유일한 원인이 이 쿼리였는지, 배포 후 알람이 해소됐는지도 입증하지 못했다.

통계 시나리오 테스트는 있지만 세부 수치 assertion이 주석 처리돼 있다. 저장 수량 재사용의 정합성을 확인하려면 생성부터 만료까지의 assertion과 수량 불일치 사례를 보강해야 한다. 성능은 대표 파라미터의 반복 측정과 운영 지연시간 분포로 추가 확인할 필요가 있다.
