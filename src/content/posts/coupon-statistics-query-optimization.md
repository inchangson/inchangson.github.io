PostgreSQL 메모리 사용률 알람이 발생한 시간대의 애플리케이션 로그와 APM 기록을 대조하는 과정에서 쿠폰 통계 조회가 느린 쿼리 후보로 식별됐다. 이 API는 쿠폰 묶음 하나에 대해 전체 수량, 할당 수량, 사용 수량처럼 서로 다른 의미의 집계를 한 응답에 조합하고 있었다. 겉으로는 한 번의 조회지만 내부에서는 원장과 이력 테이블을 대상으로 여러 `COUNT`가 실행되는 구조였다.

운영 관측과 상관관계 분석이 병목 후보를 찾는 출발점이 되었고, 나는 이후 대안 설계와 애플리케이션 코드·인덱스의 운영 반영을 담당했다. 다만 알람과 느린 쿼리가 같은 시간대에 관측됐다는 사실만으로 해당 쿼리가 메모리 알람의 유일한 원인이었다고 단정하지 않는다. 배포 후 알람 해소나 운영 지연시간 개선을 입증하는 시계열 지표도 남아 있지 않다.

이 글에서는 사내 API 경로와 실제 스키마·테이블 이름을 일반화한다. 확인 가능한 결과는 특정 데이터 조건에서 수행한 한 번의 `EXPLAIN (ANALYZE, BUFFERS)` 전후 비교와 실제 반영된 두 가지 변경이다.

## 하나의 통계 응답에 성격이 다른 세 집계가 있었다

통계 서비스의 핵심 흐름을 단순화하면 다음과 같았다.

| 집계 | 기존 계산 방식 | 검토 포인트 |
|---|---|---|
| 전체 발급 수 | 쿠폰 원장 행을 매번 `COUNT` | 이미 상위 묶음에 저장된 목표 수량을 재사용할 수 있는가 |
| 사용된 쿠폰 수 | 발급 이력에서 묶음별 `COUNT(DISTINCT coupon_id)` | 필터와 중복 제거를 인덱스 순서로 지원할 수 있는가 |
| 미할당 쿠폰 수 | 원장에서 묶음·할당 상태·유효 여부로 `COUNT` | 조건의 선택도와 실제 데이터 분포에 맞는 별도 설계가 필요한가 |

세 쿼리를 한꺼번에 “인덱스를 추가하면 된다”로 다루지 않았다. 전체 발급 수는 이미 존재하는 도메인 값으로 대체할 여지가 있었고, 사용 수 집계는 조회 자체가 필요한 대신 접근 경로를 줄일 수 있었다. 반면 미할당 수 집계는 당시 검토 자료에 실행 계획과 후보 인덱스만 있었을 뿐, 최종 적용 사실이 확인되지 않아 이번 구현 범위와 성과에서 제외했다.

제약도 분명했다.

- 통계 응답의 수치 의미를 바꾸면 안 됐다.
- `DISTINCT`는 한 쿠폰에 여러 이력 행이 생길 수 있는 모델에서 중복 집계를 막기 때문에 임의로 제거할 수 없었다.
- 조회를 빠르게 만들기 위해 별도 집계 데이터를 두면 갱신 시점과 정합성 책임이 새로 생겼다.
- 운영 반영은 애플리케이션 변경과 데이터베이스 변경을 함께 관리해야 했다.

## 첫 번째 선택: 계산하지 않아도 되는 수는 다시 세지 않는다

전체 발급 수는 쿠폰 묶음을 만들 때 이미 저장하는 수량 필드와 의미가 겹쳤다. 기존 서비스는 쿠폰 원장의 행 수를 다시 집계했지만, 변경 후에는 묶음 한 건을 조회해 그 수량을 통계 응답의 전체 수로 사용하도록 했다. 실제 코드에도 이전 `COUNT` 호출이 제거되고 상위 엔터티의 수량 필드를 읽는 경로가 남아 있다.

이 선택의 장점은 인덱스로 `COUNT`를 가속하는 수준을 넘어, 원장에 대한 집계 자체를 요청 경로에서 없앤다는 데 있다. 대신 상위 엔터티의 수량과 실제 생성된 쿠폰 수가 일치한다는 도메인 불변식이 전제된다. 구현 저장소에는 쿠폰 파일의 행 수와 묶음 수량이 다르면 오류로 처리하는 방어 로직이 있지만, 모든 생성·수정 경로의 정합성을 이 자료만으로 완전히 증명할 수는 없다. 그래서 후속 검증 항목으로 다음을 남겼다.

- 쿠폰 생성 완료 시점에 저장 수량과 실제 생성 건수가 일치하는지 확인한다.
- 재발급·취소·무효화가 “전체 발급 수”의 의미를 바꾸는지 점검한다.
- 두 값의 불일치를 탐지하는 주기적 검증이나 운영 지표를 둔다.

즉, 이미 가진 값을 읽는 방식은 가장 작은 조회 비용을 만들지만 그 값의 생명주기를 신뢰할 수 있을 때만 안전하다.

## 두 번째 선택: 필터와 DISTINCT의 입력 순서를 한 인덱스로 맞춘다

사용된 쿠폰 수는 발급 이력에서 묶음 식별자로 필터링한 뒤 쿠폰 식별자의 중복을 제거해야 했다. 기존 단일 실행 계획에서는 대상 이력 약 10만 건을 얻기 위해 테이블 전체를 순차 스캔했고, 이후 쿠폰 식별자를 정렬해 집계했다.

여기에는 `(묶음 식별자, 쿠폰 식별자)` 순서의 복합 인덱스를 적용했다. 첫 번째 컬럼은 `WHERE` 조건으로 특정 묶음의 범위를 좁히고, 두 번째 컬럼은 그 범위 안에서 `DISTINCT` 대상이 정렬된 형태로 공급되도록 한다. 이 순서는 단순히 쿼리에 등장한 컬럼을 나열한 것이 아니라 **동등 조건으로 범위를 정한 다음, 집계에 필요한 값을 읽는 접근 패턴**에 맞춘 것이다.

적용 전후의 한 번 측정은 다음과 같았다.

| 항목 | 적용 전 | 적용 후 |
|---|---:|---:|
| 주요 접근 경로 | Sequential Scan + Sort + Aggregate | Index Only Scan + Aggregate |
| 실행 시간 | 34.802ms | 14.510ms |
| 실행 단계의 공유 버퍼 블록 | hit 4,227 | hit 1 + read 386, 합계 387 |
| Heap Fetches | 해당 없음 | 0 |

이 수치는 운영 KPI가 아니라 특정 조건에서 얻은 **단 한 번의 실행 계획 비교**다. 적용 전은 공유 버퍼 hit로만 기록됐고 적용 후에는 디스크 read가 포함돼 있어 캐시 상태도 동일하게 통제됐다고 볼 수 없다. 따라서 이 결과로 평균·상위 백분위 응답시간이나 메모리 절감률을 주장하지 않는다. 다만 같은 형태의 집계에서 순차 스캔과 별도 정렬이 사라지고, 실행 단계가 접근한 블록이 4,227개에서 총 387개로 줄어든 계획 변화는 확인할 수 있었다.

## Index Only Scan은 인덱스를 만들었다고 항상 유지되지 않는다

측정 당시 `Heap Fetches: 0`이었던 이유는 인덱스에 필요한 두 컬럼이 모두 있고, PostgreSQL이 Visibility Map을 통해 대상 힙 페이지의 행들이 현재 스냅샷에서 보인다고 판단할 수 있었기 때문이다.

하지만 인덱스에는 각 행 버전의 가시성 정보가 없다. 쓰기가 발생해 페이지가 all-visible 상태가 아니면 PostgreSQL은 인덱스에서 위치를 찾은 뒤 힙을 방문해 가시성을 확인해야 한다. 테이블 갱신 패턴과 autovacuum 상태에 따라 같은 쿼리도 `Heap Fetches`가 늘 수 있다는 뜻이다.

따라서 이번 실행 계획은 “항상 힙 접근이 0이다”라는 보장이 아니라, 측정 시점에 인덱스만으로 처리할 수 있었음을 보여 주는 증거로 해석했다. 운영 검증에서는 실행 시간뿐 아니라 다음 항목을 함께 봐야 한다.

- `Heap Fetches`와 shared buffer hit/read 추이
- 실제 파라미터별 대상 행 수와 묶음별 데이터 편차
- 인덱스 크기와 발급 이력 쓰기 비용
- autovacuum 진행 상태와 테이블 갱신 빈도

## 물리화 뷰와 요약 테이블도 검토했지만 적용하지 않았다

`COUNT(DISTINCT ...)`를 요청마다 수행하지 않는 방법도 검토했다.

| 대안 | 얻는 것 | 추가로 감당할 것 |
|---|---|---|
| 복합 인덱스 | 원본 데이터의 최신 상태를 그대로 조회하면서 읽기 범위 축소 | 인덱스 저장 공간과 쓰기·vacuum 비용 |
| 물리화 뷰 | 미리 계산한 결과를 빠르게 조회 | refresh 주기, 최신성 지연, 스케줄러와 실패 복구 운영 |
| 요약 테이블 + 고유 매핑 | 신규 조합일 때만 카운터를 증가시켜 조회 비용 최소화 | 이력 쓰기와 요약 갱신의 원자성, 재처리·보정 로직, 추가 테이블 운영 |

물리화 뷰는 발급 작업처럼 갱신 시점을 예측할 수 있으면 이벤트나 스케줄 기반 refresh를 설계할 수 있지만, 그 사이의 통계는 최신이 아닐 수 있다. 요약 테이블은 조회를 가장 단순하게 만들 수 있는 대신 `(묶음, 쿠폰)` 조합의 최초 발생을 고유하게 보장하고 카운터 갱신까지 일관되게 묶어야 한다.

이번에는 이 두 방식을 **검토 대안으로만 남기고 구현하지 않았다**. 원본에서 즉시 계산한다는 기존 의미를 유지하면서 변경 범위를 제한할 수 있는 복합 인덱스와, 이미 존재하던 묶음 수량의 재사용을 선택했다. 트래픽과 데이터가 더 커져 인덱스만으로 목표를 충족하지 못할 때는 최신성 요구를 먼저 합의한 뒤 물리화 뷰나 요약 테이블을 다시 판단해야 한다.

## 코드와 실행 계획을 서로 다른 검증 층으로 사용했다

애플리케이션 코드에서는 통계 엔드포인트가 호출하는 서비스와 저장소까지 추적해 다음을 확인했다.

- 전체 수 계산이 원장 `COUNT`에서 묶음 수량 조회로 바뀌었는가
- 사용 수 계산이 여전히 묶음별 고유 쿠폰 수라는 의미를 유지하는가
- 전체 수를 이용해 할당·미사용 수를 파생하는 기존 응답 구조가 유지되는가

저장소에는 쿠폰을 생성·등록·사용·만료한 뒤 통계 엔드포인트를 호출하는 시나리오 테스트가 있다. 다만 통계 필드에 대한 세부 assertion은 주석 처리돼 있어, 이것만으로 변경 후 수치 정합성이 자동 검증됐다고 주장할 수는 없다. 상위 수량을 재사용한 변경에는 상태 전이별 assertion을 복원하고, 저장 수량과 실제 행 수가 어긋난 실패 사례를 추가하는 것이 필요하다.

데이터베이스에서는 `EXPLAIN (ANALYZE, BUFFERS)`로 실행 노드, 실제 행 수, 정렬 유무, buffer, heap fetch를 비교했다. 실행 계획은 “빨라졌다”는 결과뿐 아니라 왜 달라졌는지 확인하는 도구였다. 다만 한 번의 측정만 남아 있으므로 대표 파라미터 여러 개와 반복 측정, 동시 요청 부하, 운영 APM의 p50·p95·p99를 연결하는 검증은 후속 과제로 남는다.

## 결과와 회고

실제로 반영한 변경은 두 가지다. 전체 수 집계를 기존 묶음 수량 조회로 대체했고, 사용 수 집계에는 `(묶음 식별자, 쿠폰 식별자)` 복합 인덱스를 적용했다. 한 번의 실행 계획 비교에서는 사용 수 집계가 Sequential Scan과 Sort에서 Index Only Scan으로 바뀌었고, 실행 시간은 34.802ms에서 14.510ms로, 실행 단계의 접근 블록은 4,227개에서 387개로 변했다.

여기서 가장 중요한 회고는 숫자를 크게 보이게 만드는 것이 아니라 증거의 경계를 지키는 일이다. 관측 상관관계는 원인 증명이 아니고, 단일 실행 계획은 운영 성과 지표가 아니며, 검토한 설계는 구현한 설계가 아니다. 반대로 그 경계를 명확히 하면 이번 개선의 기술적 판단은 더 선명해진다. 계산할 필요가 없는 값은 데이터 모델에서 재사용하고, 반드시 계산해야 하는 값은 실제 필터와 중복 제거 순서에 맞는 접근 경로를 제공했다.

다음 단계에서는 배포 전후 동일 조건의 반복 측정과 운영 지연시간 분포를 수집하고, 상위 수량의 정합성을 자동 검증하며, 인덱스의 쓰기 비용과 `Heap Fetches` 추이를 함께 관찰해야 한다. 그 자료가 쌓여야 알람 해소나 운영 성능 개선을 책임 있게 말할 수 있다.
